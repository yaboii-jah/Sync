## Open Questions

- Nothing verifies that a link an attendee types belongs to them — Connect and Settings accept any approved LinkedIn, Instagram, Facebook, or profile-shaped GitHub URL, so a card can point at someone else's profile. The card auto-activates when links exist and carries the attendee's own Google name and photo beside them, which limits the damage without preventing it. GitHub account type is intentionally not verified because user and organization root URLs have the same shape.
- The historical migration chain is not replayable from an empty database: `20260902120000_social_profiles.sql` unconditionally recreates a table already created by `20260901152106`. The remote project is current and the new migrations are applied, but repairing this requires a deliberate migration-history rewrite or squash rather than editing an applied migration.
- A session that finishes on schedule reads `started N ago` on its card rather than `ended N ago`, because the end anchor fires only on an operator override. Choosing which time the card should anchor to needs a product decision, so it was left alone during the home UI fix batch.
- An empty-string `events.venue` would render an empty hero venue label and the accessible name `Open  in Google Maps`. The fallback uses `??`, which is what the decision asked for, and `??` only covers null. Reachability is low: the column is nullable, carries no check constraint, and no admin write path sets it.
- `PushGate`'s `busy` stage has no timeout, so if `Notification.requestPermission()` never settles the install card is held indefinitely. Not reachable by a real user click, and deliberately not fixed.
- `relativeMagnitude` floors where `formatRelativeTime` rounds, so a session 119 minutes out reads `in 1 hr` on its card.
- The `merch_attendees` / `merch_scan_log` tables and the `merch_claim_attendee` / `merch_revert_claim` functions exist in the project with no migration row and no application code in any branch. They are in `database.types.ts` because it is generated from the remote schema. Whoever owns them should land their migration

## Environment Setup Requirements

- **Supabase Auth redirect allowlisting**: GoTrue only honors OAuth `redirect_to` targets listed under Dashboard → Authentication → URL Configuration → Redirect URLs; anything else silently falls back to the Site URL and drops the auth code on an unhandled page. Required entries: `http://localhost:3000/auth/callback` for local dev, plus each deployed origin's `/auth/callback` when hosting is finalized. ## Architecture Decisions

- **Next.js + Supabase, with PWA integration** — chosen for a single stack covering frontend, auth, database, and realtime, plus an installable home-screen experience for attendees
- **Google OAuth via Supabase Auth** — auto-fills name, email, and photo. Networking links are optional, attendee-supplied data and are unrelated to authentication.
- **Public bearer networking cards** — one stable high-entropy app URL resolves through a narrow anonymous RPC only while its owner has at least one saved link; underlying profile, card, and social tables remain inaccessible to anonymous clients.
- **Allowlisted admin operations workspace** — `/admin` provides event-day notification, delivery, session-state, attendee lookup, and audit tools; authorization is enforced by `admin_users`, admin-only RPCs, and RLS rather than route visibility alone.
- **Smart notification model** — pg_cron creates session reminders and live/wrapped alerts; all eligible notification rows appear in Alerts; automated session alerts target snapshotted bookmarkers, while admins can immediately send to everyone or selected attendees. Every push dispatch records recipient/device outcomes and retries bounded transient failures.
- **Workshop registration deferred to a later phase** — the 3-workshop, 39-slot, QR-check-in system (with a decided ~24h Pro-pass early-access window) is out of scope for the initial build
- **Two-layer realtime design** — Supabase Realtime (Postgres change subscriptions) keeps the app in sync while open; Web Push API via the service worker handles notifications when the app is closed. These are treated as separate systems, not one feature
